Enroll 檔案有 <M t="r = 200{,}000" /> 筆紀錄，<M t="\text{bfr} = 20" />，共 <M t="b = 10{,}000" /> 個區塊。查詢「grade 介於 80 到 89 的所有選課」，已知符合的紀錄約佔 10%，也就是 20,000 筆。比較下列三種做法要讀幾個區塊：

(a) 堆積檔，沒有任何索引。

(b) 檔案依 grade 排序，在 grade 上有一個 3 層的叢集索引。

(c) 檔案沒有依 grade 排序，grade 上有一個 B+ 樹次要索引：樹高 3（找到第一個葉子要讀 3 個區塊），每個葉子放 100 個（grade, 紀錄指標），符合的紀錄散在不同區塊。

<Solution>

**(a) 10,000。(b) 1,003。(c) 20,202。**

**(a)** 沒有索引，只能讀完整個檔案：10,000 個區塊。

**(b)** 用叢集索引找到 80 分的第一個區塊，讀 3 個索引區塊；資料依 grade 排序，所以 20,000 筆符合的紀錄**連續**存放，佔 <M t="20000 / 20 = 1000" /> 個區塊。共 <M t="3 + 1000 = 1003" /> 個。

**(c)** 搜尋到 80 分所在的葉子要讀 3 個區塊；20,000 個項目佔 <M t="20000 / 100 = 200" /> 個葉子，第一個已經讀了，沿葉子鏈再讀 199 個；資料沒有依 grade 排序，每筆符合的紀錄最壞情況各在不同的區塊，要讀 20,000 個。共 <M t="3 + 199 + 20000 = 20{,}202" /> 個。

**結論**：(c) 比完全不用索引的 (a) 還慢一倍。符合的比例高時，次要索引的每一筆都要額外讀一個資料區塊，不如直接掃描整個檔案。這就是第 8 章查詢最佳化要估計「選擇率」的原因；只有符合的筆數很少時，次要索引才划算。

</Solution>
