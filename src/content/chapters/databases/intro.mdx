### 檔案系統與 DBMS

#### 為什麼需要資料庫

想像一所學校還沒有資料庫的時候：註冊組、教務處、圖書館各自寫了自己的程式，各自把學生資料存成自己的檔案。每個單位都存了一份「學號、姓名、系」，格式還不一樣（見圖 1-1 左半）。這種作法叫**檔案處理系統**（file-processing system）。改用資料庫之後，所有程式都透過一套專門管理資料的軟體，也就是**資料庫管理系統**（DBMS，下面會正式定義），存取同一份資料（圖 1-1 右半）。

<Figure no="1-1" caption="左：每個應用程式各自擁有檔案，同一份學生資料存了三次。右：應用程式都透過 DBMS 存取同一個資料庫，資料只存一份。">
  <FileVsDbms />
</Figure>

檔案處理系統的問題會隨著單位變多而越來越嚴重。每一項問題後面接著寫 DBMS 怎麼解決：

- **資料重複**（redundancy）與**不一致**（inconsistency）：學生轉系，註冊組改了，圖書館的檔案還是舊的系。DBMS 把資料集中存一份，所有程式看到同一份。
- **存取困難**：想要「資管系借書超過 10 本的學生」，就得寫一支新程式去讀兩個格式不同的檔案。DBMS 提供查詢語言（SQL），直接問就好，不必寫新程式。
- **完整性**（integrity）**問題**：「學號不能重複」寫在每支程式裡，新程式忘了檢查，就會存進重複的學號。DBMS 把限制寫在資料庫的定義裡，統一檢查。
- **原子性**（atomicity）**問題**：加選一門課要「扣名額」和「新增選課紀錄」兩步，做到一半當機，名額就少了一個。DBMS 提供交易（transaction）：要嘛全部完成，要嘛全部不做。
- **並行存取異常**：兩個學生同時搶最後一個名額，兩支程式都讀到「還剩 1 個」，結果兩人都選上。DBMS 的並行控制讓同時進行的存取不互相干擾。
- **安全問題**：圖書館的程式能讀到整個學生檔，包括成績。DBMS 用授權限制每個使用者只能看、只能改被允許的部分。

這幾項後面各有一章深入：完整性見第 3 章，交易與並行控制見第 9 章。

#### 資料庫、DBMS 與資料庫系統

三個名詞常一起出現，要分清楚：

> **定義**：**資料庫**（database）是一群彼此相關的資料的集合。**資料庫管理系統**（database management system，DBMS）是讓使用者定義、建立、查詢、更新與維護資料庫的軟體。資料庫加上 DBMS（再加上使用它們的應用程式）合稱**資料庫系統**（database system）。

例如：MySQL、PostgreSQL、Oracle 是 DBMS；學校存在 PostgreSQL 裡的學生、課程與選課資料是資料庫。

#### 誰在使用資料庫

| 角色 | 做什麼 |
|---|---|
| 資料庫管理師（database administrator，DBA） | 定義綱要、授權、備份與回復、監控與調校效能 |
| 應用程式設計師 | 寫存取資料庫的程式（例如選課系統） |
| 一般使用者 | 透過應用程式的畫面使用資料，或直接下查詢 |

#### 限制：DBMS 不是零成本

DBMS 本身要授權費、要硬體、要有人管理；它為了安全、並行控制與回復做的額外工作，也會讓單純的讀寫變慢。如果只是一支單一用途、只有一個人用的小程式（例如一份設定檔），直接用檔案反而簡單。

另外，DBMS 並沒有消滅**所有**重複。為了效能，設計者有時會刻意保留一些重複的資料（例如在訂單上多存一份商品名稱），但這份重複由 DBMS 統一管理、會一起更新，稱為**受控的冗餘**（controlled redundancy）。檔案系統的問題是「不受控」的重複。

### 三層綱要架構

#### 綱要與實例

先分清楚兩個常被混用的詞：

- **綱要**（schema）：資料庫的**結構描述**：有哪些表、每個表有哪些欄位、型別與限制。設計好之後很少改。
- **實例**（instance）：資料庫在**某一個時刻**實際存的資料，又叫資料庫狀態（state）。每次新增、修改、刪除都會變。

類比寫程式：綱要像型別宣告 `int age`，實例像變數此刻的值 `age = 20`。有些課本把綱要叫**內涵**（intension）、實例叫**外延**（extension）。

學校的例子：「學生有學號 sid、姓名 name、系 dept」是綱要，記作 Student(sid, name, dept)；「S1 王小明 資管、S2 李美華 資工」這兩筆是此刻的實例。新生入學、學生轉系，改變的都是實例；替學生多加一個 email 欄位，改變的才是綱要。

#### 為什麼要分三層

同一個資料庫有很多種使用者，他們需要的東西不一樣：

- 圖書館只需要學號和姓名，而且**不應該**看到成績。
- 寫查詢的人只關心「有哪些表、表之間有什麼關係」，不想知道資料存在哪顆硬碟、用什麼檔案格式。
- DBA 要決定資料怎麼存才快：要不要建索引、檔案怎麼排。

如果這三種需求都寫在同一份描述裡，改任何一個細節都會牽動所有人。所以美國國家標準協會（ANSI/SPARC）在 1975 年提出把綱要分成三層：

> **定義**：**三層綱要架構**（three-schema architecture）把資料庫的描述分成三層：**外部層**（external level）描述各使用者群看到的部分；**概念層**（conceptual level）描述整個資料庫有哪些資料、關係與限制；**內部層**（internal level）描述資料實際上怎麼存放。

外部層又叫視界層（view level），概念層又叫邏輯層（logical level），內部層又叫實體層（physical level）。三層的數量不同：

| 層 | 數量 | 學校的例子 |
|---|---|---|
| 外部層 | **很多個**，每個使用者群一個 | 圖書館看到 (sid, name)；教務處看到 (sid, name, 平均成績) |
| 概念層 | **一個** | Student(sid, name, dept)、Course(cid, title)、Enroll(sid, cid, grade) 三個表，以及「sid 不能重複」等限制 |
| 內部層 | **一個** | Student 依 sid 排序存成檔案，在 dept 上建索引 |

表中的 Course 是課程（cid 是課號、title 是課名），Enroll 是選課紀錄（哪位學生 sid 修了哪門課 cid、成績 grade）。

注意教務處看到的「平均成績」並沒有存在概念層裡：它是從 Enroll 的 grade 算出來的。外部綱要可以只取一部分欄位，也可以加上計算出來的欄位。

#### 兩個對映

三層之間靠**對映**（mapping）連起來。對映的工作是**翻譯**：把上一層的請求翻成下一層聽得懂的請求。

- **外部／概念對映**：說明外部綱要的每個欄位，是從概念綱要的哪些表、哪些欄位得到的。每一個外部綱要都有自己的一個。
- **概念／內部對映**：說明概念綱要的每個表，實際上存在哪個檔案、用什麼結構。只有一個。

<Figure no="1-2" caption="三層綱要架構：外部綱要可以有很多個，概念綱要與內部綱要各一個；相鄰兩層之間各有一層對映。">
  <ThreeSchema />
</Figure>

照著圖 1-2 走一次圖書館的查詢「學號 S2 的姓名」：

1. 圖書館的程式對自己的外部綱要下查詢：「從 (sid, name) 找 sid = S2 的 name」。
2. **外部／概念對映**把它翻成概念層的查詢：「從 Student 表找 sid = S2 的 name」。
3. **概念／內部對映**把它翻成內部層的操作：「Student 存在某個檔案、依 sid 排序，用二分搜尋找到 S2 所在的磁碟區塊並讀進來」。
4. 結果沿著原路往上傳，圖書館只拿到姓名，看不到 dept 和成績。

#### 限制

每多一層對映，查詢就要多翻譯一次，這是三層架構的成本。而且三層是一個**概念上的架構**，實際的 DBMS 不一定把三層分得這麼清楚；例如在 SQL 裡，外部綱要通常就是用檢視表（view，第 5 章）來做。

### 資料獨立性

#### 為什麼需要資料獨立性

分三層的真正目的，是讓**改一層的時候，不必改到上一層**。在檔案系統裡，程式直接讀檔案，檔案格式一改（例如多加一個欄位），所有讀這個檔案的程式都要跟著改。資料庫希望做到的是：DBA 調整儲存方式、或設計者調整表的結構時，已經寫好的應用程式不用動。

> **定義**：**資料獨立性**（data independence）是修改某一層的綱要時，不必修改上一層綱要的能力。改變只會影響兩層之間的對映。

依「改的是哪一層」分成兩種，見圖 1-3。

<Figure no="1-3" caption="黑底是被修改的那一層，粗線是唯一需要跟著改的對映；它上面的各層都不受影響。">
  <Independence />
</Figure>

#### 實體資料獨立性

> **定義**：**實體資料獨立性**（physical data independence）是修改**內部綱要**時，不必修改概念綱要（因此也不必修改外部綱要與應用程式）的能力。

例子（都只改「資料怎麼存」，不改「存了什麼」）：

- 在 Student 的 dept 欄位上建一個索引，讓「找某系的學生」變快。
- 把 Student 的檔案從循序檔改成雜湊檔。
- 把資料檔搬到另一顆硬碟，或開啟壓縮。

這些改變都只需要修改**概念／內部對映**：告訴 DBMS「Student 現在改存在這裡、改用這種結構」。查詢「Student 裡 sid = S2 的人」在概念層的寫法完全不變。

#### 邏輯資料獨立性

> **定義**：**邏輯資料獨立性**（logical data independence）是修改**概念綱要**時，不必修改外部綱要（因此也不必修改應用程式）的能力。

例子（改的是「存了什麼、怎麼分表」）：

- 在 Student 加一個 email 欄位。用不到 email 的外部綱要不受影響。
- 新增一個 Dept 表。
- 把一個表拆成兩個（下面的例子）。

這些改變需要修改**外部／概念對映**：重新說明「外部綱要的每個欄位，現在要從哪裡得到」。

#### 例：一步一步把表拆開，應用程式卻不用改

**目標**：教務處的程式用的外部綱要是 (sid, name, dept_phone)，其中 dept_phone 是學生所屬系的系辦電話。現在要修改概念綱要，但教務處的程式不能改。

**原本的概念綱要**：系辦電話直接存在學生表裡，同一系的每個學生都存一次電話：

```
Student(sid, name, dept, dept_phone)
```

教務處的外部綱要是 Student 的一部分欄位，用 SQL 的檢視表寫成：

```
CREATE VIEW Office AS
    SELECT sid, name, dept_phone
    FROM Student;
```

**想法**：電話重複存很多次，系辦換電話就要改很多列，漏改一列就不一致（這正是第 6 章「正規化」要處理的問題）。所以把「系的資料」拆到自己的表；拆完之後，只要重新說明 Office 的 dept_phone 從哪裡來，教務處就感覺不到差別。

**步驟**：

1. 修改概念綱要，拆成兩個表。每個系的電話只存一次：

```
Student(sid, name, dept)
Dept(dept, phone)
```

2. 修改外部／概念對映，也就是重新定義檢視表：dept_phone 改成「用學生的 dept 到 Dept 表找出的 phone」：

```
CREATE VIEW Office AS
    SELECT s.sid, s.name, d.phone AS dept_phone
    FROM Student s JOIN Dept d ON s.dept = d.dept;
```

　　`s`、`d` 是 Student 與 Dept 的簡稱；`JOIN … ON s.dept = d.dept` 把每位學生和「dept 相同的那一列 Dept」接在一起；`AS dept_phone` 把 phone 取名為 dept_phone，和原本的欄位同名。這些語法第 5 章會完整介紹。

3. 教務處的程式照舊執行 `SELECT name, dept_phone FROM Office WHERE sid = 'S2'`，得到的結果和拆表之前相同。

**結論**：概念綱要改了，外部綱要 Office 的欄位與意義沒變，只改了外部／概念對映（檢視表的定義），所以這是**邏輯資料獨立性**。內部綱要當然也要跟著存兩個表，但那是 DBMS 依新的概念綱要自動處理的部分。

#### 限制：邏輯獨立性比較難達成

兩種獨立性中，**邏輯資料獨立性比較難達成**。原因是應用程式依賴的就是概念層的結構與意義：

- **刪掉外部綱要用到的欄位**，任何對映都補不回來。例如完全不再記錄系辦電話，Office 的 dept_phone 就沒有來源，教務處的程式一定要改。
- **透過檢視表更新資料**不一定做得到。例如 Office 由兩個表合併而來，「修改某位學生的 dept_phone」到底要改哪個系的電話？第 5 章會說明哪些檢視表可以更新。

相對地，內部層的改變（索引、檔案結構）本來就看不到，只要 DBMS 改對映就好，所以實體資料獨立性容易得多。

### 資料模型

#### 什麼是資料模型

綱要要用某種「語言」來寫：資料長成什麼形狀、資料之間的關係怎麼表示、可以加哪些限制、可以做哪些操作。這組概念就是**資料模型**。

> **定義**：**資料模型**（data model）是描述資料、資料之間的關係、資料的語意與限制的一組概念工具，通常也包含一組操作。

依描述的抽象程度，分成三類：

| 類別 | 給誰看 | 例子 |
|---|---|---|
| 概念資料模型（高階） | 和使用者討論需求 | ER 模型（第 2 章） |
| 表示資料模型（實作） | DBMS 實際採用 | 階層式、網路式、關聯式 |
| 實體資料模型（低階） | 描述存放細節 | 檔案結構、索引 |

考試最常問的是三種表示資料模型的比較。下面用同一份選課資料，看它們各自怎麼表示：兩門課 C1、C2，三位學生 S1、S2、S3；S1 修了兩門課，S2 修 C2，S3 修 C1。這是**多對多**（M:N）的關係：一門課有多位學生，一位學生也可以修多門課。

#### 階層式模型

**階層式模型**（hierarchical model）把資料排成**樹**：每筆紀錄（record）最多只有一個父紀錄，父子之間是一對多（1:N）。代表系統是 IBM 的 IMS（1960 年代）。

圖 1-4 以課程為父、學生為子，問題立刻出現：S1 修了兩門課，就要有**兩個**父紀錄，但樹不允許。只好把 S1 存兩份（或用「虛擬紀錄」指向同一份）。所以階層式模型**不擅長表示多對多**。

樹狀結構還會帶來三種操作上的限制：

- **新增**：沒有父紀錄就不能新增子紀錄。還沒有人選的新課可以先建立，但還沒選課的新生無處可放。
- **刪除**：刪掉父紀錄，底下所有子紀錄也一起刪除。如果某位學生只修了 C1，刪掉 C1 這門課，這位學生的資料就從資料庫裡消失了。
- **查詢**：要從根往下一層一層走。「S1 修了哪些課」要走過每一門課，看底下有沒有 S1。

#### 網路式模型

**網路式模型**（network model）把資料排成**圖**：一筆紀錄可以有多個「父紀錄」。它由 CODASYL 的 DBTG 委員會在 1971 年定出標準，以**集合型態**（set type）表示一對多的關係：一端是**擁有者**（owner），另一端是**成員**（member）。

集合型態本身只能表示 1:N，多對多要再加一種**連結紀錄**（link record）：每一筆選課是一筆連結紀錄，它同時是「某門課」的成員、也是「某位學生」的成員。圖 1-4 中 S1 只存一份，透過兩筆連結紀錄連到 C1 和 C2，沒有重複。

代價是結構複雜：紀錄之間用**指標**串起來，程式要自己沿著指標一筆一筆走（「找到 S1 → 找它的第一筆連結紀錄 → 找下一筆 → ……」），資料的結構一改，走法就要跟著改。

#### 關聯式模型

**關聯式模型**（relational model）由 E. F. Codd 在 1970 年提出，把所有資料都表示成**表**（關聯，relation）。選課就是一個 Enroll(sid, cid) 表，一列代表一筆選課。

關係不靠指標，而是靠**相同的值**：Enroll 的某一列寫著 (S1, C1)，就表示 S1 修了 C1；要知道 S1 的姓名，就到 Student 表找 sid 也是 S1 的那一列。使用者只要說「要什麼」，不必說「怎麼走」，DBMS 會自己決定怎麼找。這是今天的主流，第 3 章起都以關聯式模型為準。

#### 三種模型的比較

| | 階層式 | 網路式 | 關聯式 |
|---|---|---|---|
| 資料結構 | 樹 | 圖 | 表 |
| 關係的表示 | 父子（指標） | 擁有者與成員（指標） | 相同的屬性值 |
| 多對多 | 要重複紀錄 | 用連結紀錄 | 用一個表 |
| 查詢方式 | 程序性，從根往下走 | 程序性，沿著指標走 | 非程序性，描述要什麼 |
| 資料獨立性 | 低 | 低 | 高 |

#### 其他模型

**物件導向模型**把資料和操作包成物件，**物件關聯式模型**則在關聯式上加入物件的功能（例如自訂型別）。不以表為主的 **NoSQL** 系統（鍵值、文件、圖形資料庫）用在需要大量水平擴充的場合。這些通常只考名詞，知道它們的存在即可。

### 資料庫語言

#### 三類語言

DBMS 提供的語言依用途分成三類：**資料定義語言**（data definition language，DDL）、**資料操作語言**（data manipulation language，DML）與**資料控制語言**（data control language，DCL）。今天幾乎所有關聯式 DBMS 都用 **SQL**（Structured Query Language），三類都包含在 SQL 裡：

| 類別 | 用途 | SQL 敘述 |
|---|---|---|
| DDL | 定義與修改**綱要** | `CREATE`、`ALTER`、`DROP` |
| DML | 查詢與修改**實例** | `SELECT`、`INSERT`、`UPDATE`、`DELETE` |
| DCL | 控制**權限** | `GRANT`、`REVOKE` |

判斷的方法是問：這個敘述改的是**結構**、**資料**，還是**誰能做什麼**？

```
CREATE TABLE Student (            -- DDL：定義 Student 的綱要
    sid   CHAR(5) PRIMARY KEY,
    name  VARCHAR(20),
    dept  VARCHAR(10)
);
INSERT INTO Student VALUES ('S1', '王小明', '資管');   -- DML：新增一筆資料
GRANT SELECT ON Student TO library;                    -- DCL：讓圖書館可以查詢
```

`CHAR(5)` 是長度固定為 5 的字串，`VARCHAR(20)` 是最長 20 個字元的字串，`PRIMARY KEY` 表示 sid 是主鍵、不能重複（第 3 章）。

容易混淆的兩組：

- `DELETE FROM Student` 刪除**所有列**，表還在（DML）；`DROP TABLE Student` 連**表本身**一起刪掉（DDL）。
- `COMMIT`、`ROLLBACK` 是交易控制；有些課本把它們歸在 DCL，有些另外分成**交易控制語言**（TCL）。題目若沒有 TCL 這個選項，就選 DCL。

#### 資料字典

DDL 執行的結果（有哪些表、欄位、型別、限制、索引、誰有什麼權限）本身也是資料，稱為**詮釋資料**（metadata），存在 DBMS 的**資料字典**（data dictionary），又叫**系統目錄**（system catalog）。DBMS 處理每一個查詢時，都要先查資料字典，才知道 Student 有沒有 dept 這個欄位、上面有沒有索引。

#### 程序性與非程序性 DML

DML 又依「要不要說明怎麼找」分成兩種：

- **程序性**（procedural）DML：使用者要指定**要什麼**，以及**怎麼找到它**，通常一次處理一筆紀錄（record-at-a-time）。階層式與網路式模型的 DML 屬於這種。
- **非程序性**（non-procedural，又叫宣告式 declarative）DML：使用者只指定**要什麼**，怎麼找由 DBMS 決定，一次處理一整組資料（set-at-a-time）。SQL 屬於這種。

同樣是「找出資管系所有學生的姓名」：

```
-- 非程序性（SQL）：只說要什麼
SELECT name FROM Student WHERE dept = '資管';

-- 程序性（網路式模型風格的偽代碼）：自己一筆一筆走
找到 Student 的第一筆紀錄
while 還有紀錄
    if 這筆的 dept = '資管': 輸出 name
    找到下一筆紀錄
```

非程序性語言好寫，但 DBMS 必須自己想出一個有效率的找法，這就是第 8 章「查詢最佳化」要做的事。

#### 一個查詢經過 DBMS 的哪些元件

最後把前面的東西串起來。DBMS 內部大致分成兩大塊（見圖 1-5）：

- **查詢處理器**（query processor）：把 SQL 翻成執行計畫。**DDL 直譯器**處理 DDL、把結果寫進資料字典；**DML 編譯器**把查詢翻成關聯代數（第 4 章），**查詢最佳化器**從多種做法中挑一個成本最低的；**查詢執行引擎**照計畫執行。
- **儲存管理員**（storage manager）：負責和磁碟打交道。**授權與完整性管理員**檢查權限與限制；**交易管理員**負責交易與並行控制；**檔案管理員**管理磁碟上的空間；**緩衝區管理員**決定哪些磁碟區塊要放在記憶體裡。

磁碟上存的有：資料檔、索引、資料字典，以及回復用的日誌（第 10 章）。

  <DbmsComponents />
</Figure>

以 `SELECT name FROM Student WHERE dept = '資管'` 為例：

1. **DML 編譯器**查資料字典，確認 Student 表和 name、dept 欄位存在，翻成內部的表示。
2. **查詢最佳化器**查資料字典發現 dept 上有索引，比較「整個檔案掃一遍」和「用索引找」的成本，選擇成本低的那個。
3. **查詢執行引擎**照計畫向儲存管理員要資料。
4. **授權管理員**確認這個使用者有 Student 的 `SELECT` 權限；**緩衝區管理員**把需要的磁碟區塊讀進記憶體（已經在記憶體裡就不必再讀）。
5. 符合條件的 name 傳回給使用者。

這條路線也解釋了實體資料獨立性怎麼做到的：DBA 把 dept 的索引刪掉，第 2 步會改選「整個檔案掃一遍」，查詢變慢，但 SQL 一個字都不用改。

### 常見陷阱

- **外部綱要可以有很多個**，概念綱要與內部綱要**各只有一個**。
- **建索引、換檔案結構、搬硬碟是實體資料獨立性**；加欄位、加表、拆表是邏輯資料獨立性。分辨的方法是問「改的是怎麼存，還是存了什麼」。
- **邏輯資料獨立性比實體資料獨立性難達成**，不是反過來。
- **綱要很少改，實例一直在變**。新增、刪除資料（即使刪光所有列）都只改實例。
- **`DELETE` 是 DML、`DROP` 是 DDL**：一個刪資料，一個刪結構。
- **DBMS 消除的是不受控的重複**，設計上刻意保留、由 DBMS 管理的受控冗餘仍然存在。
- **階層式模型的子紀錄只有一個父紀錄**，多對多要重複紀錄；可以有多個「父」的是網路式模型。
