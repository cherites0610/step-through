### 實體與屬性

#### 為什麼需要 ER 模型

設計資料庫時，不要一開始就畫表。表的欄位、主鍵、外鍵是給 DBMS 看的細節；和使用者討論需求時，大家真正在意的是「學校裡有哪些東西、它們之間有什麼關係」。先把這件事畫成一張大家都看得懂的圖，確定沒有遺漏，再轉成表（本章最後一節）。

**ER 模型**（entity-relationship model）就是這張圖的畫法，由 Peter Chen 在 1976 年提出，是第 1 章提過的「概念資料模型」。本章用的是考試最常見的 Chen 表示法。

#### 實體

> **定義**：**實體**（entity）是現實世界中可以和其他東西區別開來的一個對象，可以是具體的（學生王小明）或抽象的（「資料庫」這門課）。結構相同的實體歸為同一個**實體型態**（entity type），某一時刻所有這類實體的集合叫**實體集合**（entity set）。

這和第 1 章的「綱要與實例」是同一組概念：實體型態「學生」像綱要，此刻在學的所有學生像實例。ER 圖中，實體型態畫成**矩形**。

#### 屬性

**屬性**（attribute）描述實體的性質，例如學生的學號、姓名、生日。屬性畫成**橢圓**，用線連到它所屬的實體。

屬性可以從三個角度分類，每一種在圖上的畫法不同：

- **能不能再拆**：**簡單**（simple）屬性不能再拆，例如生日，畫成一般的橢圓。**複合**（composite）屬性由幾個子屬性組成，例如姓名＝姓＋名，畫成橢圓再連出子屬性的橢圓。
- **有幾個值**：**單值**（single-valued）屬性每個實體只有一個值，例如生日。**多值**（multivalued）屬性每個實體可以有多個值，例如電話（手機、住家），畫成**雙橢圓**。
- **要不要存**：**儲存**（stored）屬性實際存下來，例如生日。**衍生**（derived）屬性可以由其他屬性算出來，例如年齡（由生日和今天的日期算出），畫成**虛線橢圓**。

三個角度互相獨立：一個屬性可以同時是「複合、單值、儲存」。

#### 鍵屬性

> **定義**：值在實體集合中**不會重複**、可以用來唯一識別每一個實體的屬性，稱為**鍵屬性**（key attribute）。ER 圖中鍵屬性的名稱加**底線**。

學號就是學生的鍵屬性：知道學號，就知道是哪一位學生。一個實體型態可以有不只一個鍵（學號、身分證字號都不會重複），鍵也可以由幾個屬性合起來組成。屬性的值未知或不適用時，記為**空值**（NULL），例如還沒填的電話。

#### 該是屬性還是實體？

「系」應該是學生的一個屬性，還是一個獨立的實體？判斷的方法是問：**它自己還有沒有要記錄的性質，或者和其他東西有沒有關係？**

- 如果只需要記「學生是哪一系」，系可以只是學生的一個屬性。
- 學校還要記每個系的電話、系主任是誰，系就有了自己的屬性和關係，應該畫成實體。

本章的例子採用第二種：系是一個實體。

### 關係與基數限制

#### 關係

> **定義**：**關係**（relationship）是實體之間的關聯，例如「王小明修了資料庫」。同一類的關係歸為一個**關係型態**（relationship type），ER 圖中畫成**菱形**，用線連到參與的實體型態。

參與一個關係型態的實體型態個數，稱為它的**分支度**（degree）：

- **二元**（binary）關係：兩個實體型態，最常見。例如學生「修課」課程。
- **三元**（ternary）關係：三個實體型態。例如供應商「供應」零件給專案。
- **遞迴**（recursive）關係：同一個實體型態出現兩次。例如課程「先修」課程：資料結構是演算法的先修課。因為兩端是同一種實體，線上要標出**角色**（role），說明哪一端是「課程」、哪一端是「先修課」。

關係也可以有自己的屬性。「成績」不是學生的屬性（一位學生修很多門課，就有很多個成績），也不是課程的屬性（一門課有很多學生的成績）；它屬於「某位學生修某門課」這件事，所以是**修課**這個關係的屬性。

#### 基數比

關係的兩端各能對應幾個實體，是考試的重點。

> **定義**：二元關係的**基數比**（cardinality ratio）描述一個實體最多能和另一端的幾個實體建立這種關係，有三種：一對一（1:1）、一對多（1:N）、多對多（M:N）。

以學校為例：

- **系「屬於」學生是 1:N**：一個系有很多學生，一位學生只屬於一個系。
- **學生「修課」課程是 M:N**：一位學生修很多門課，一門課也有很多學生。
- **教師「主管」系是 1:1**：一位教師最多主管一個系，一個系只有一位主管。

在 ER 圖上，基數比寫在線的兩端。**讀法**：想知道「一個 A 最多對應幾個 B」，就看**靠近 B 那一端**的標記。例如屬於的學生那端標 N，意思是「一個系對應 N 個學生」；系那端標 1，意思是「一位學生對應 1 個系」。

#### 參與限制

基數比說的是「最多」，參與限制說的是「最少」：

> **定義**：如果實體型態 E 的**每一個**實體都必須參與關係 R，就說 E 在 R 中是**完全參與**（total participation，又叫存在相依 existence dependency），畫成**雙線**；否則是**部分參與**（partial participation），畫成單線。

- 學校規定每位學生都要屬於一個系，所以學生在「屬於」中是完全參與（雙線）。
- 新成立的系可以還沒有學生，所以系在「屬於」中是部分參與（單線）。
- 每個系都要有主管，所以系在「主管」中是完全參與；但大多數教師不是主管，教師是部分參與。

#### (min, max) 表示法

另一種常見的畫法，是在每一端寫一對數字 (min, max)：

> **定義**：在實體型態 E 那一端標 (min, max)，表示 E 的**每一個實體**參與這個關係**最少 min 次、最多 max 次**。min = 0 就是部分參與，min ≥ 1 就是完全參與。

「屬於」寫成 (min, max)：每位學生恰好屬於一個系，所以**學生那端**標 (1, 1)；每個系有 0 到多位學生，所以**系那端**標 (0, N)。

注意標記的**位置**：基數比的 N 寫在學生那端，(min, max) 的 N 卻寫在系那端。兩種畫法的位置正好相反，這是選擇題最常設計的陷阱：

<Figure no="2-3" caption="同一個「屬於」關係的兩種畫法。基數比的標記描述「對方的一個實體對應幾個我」，(min, max) 描述「我的一個實體參與幾次」，所以 N 出現在相反的兩端。">
  <MinMaxNotation />
</Figure>

**互相轉換的步驟**（以二元關係 A—R—B 為例）：

1. 讀 A 那端的 (min, max)：A 的每個實體最多和 max 個 B 有關係。
2. 這個 max 就是**基數比中 B 那端**的標記（max = 1 標 1，否則標 N 或 M）。
3. 對 B 那端做同樣的事，得到 A 那端的標記。
4. min = 0 是部分參與（單線），min ≥ 1 是完全參與（雙線）。

套用到圖 2-3：學生那端 (1, 1) 的 max = 1，所以系那端標 1；系那端 (0, N) 的 max = N，所以學生那端標 N。學生的 min = 1，完全參與；系的 min = 0，部分參與。

#### 限制：三元關係不能任意拆成三個二元關係

「供應商 S 把零件 P 供應給專案 J」是三元關係。能不能改成三個二元關係「S 供應 P」「P 用在 J」「S 合作 J」？一般來說**不能**，因為拆開之後會失去「三者同時成立」的資訊。

**例**：原本有三筆供應紀錄 (S1, P1, J2)、(S1, P2, J1)、(S2, P1, J1)。拆成三個二元關係：

- S 供應 P：(S1, P1)、(S1, P2)、(S2, P1)
- P 用在 J：(P1, J2)、(P2, J1)、(P1, J1)
- S 合作 J：(S1, J2)、(S1, J1)、(S2, J1)

現在問：「S1 有沒有把 P1 供應給 J1？」三個二元關係都說得通：S1 供應過 P1、P1 用在 J1、S1 和 J1 合作過。但原本的三筆紀錄裡**沒有** (S1, P1, J1)。從二元關係推不出正確答案，所以這裡必須用三元關係。

### 弱實體

#### 為什麼需要弱實體

學校要記錄教師的眷屬（申請眷屬保險用），每位眷屬記姓名和關係（配偶、子女）。問題是：眷屬沒有一個全校不重複的屬性。兩位教師可能各有一個叫「王小美」的女兒，光看姓名分不出是誰。但只要加上「是哪位教師的眷屬」，就分得出來了。

> **定義**：沒有自己的鍵屬性、必須透過和另一個實體型態的關係才能識別的實體型態，稱為**弱實體型態**（weak entity type）。它所依附的實體型態稱為**識別擁有者**（identifying owner），兩者之間的關係稱為**識別關係**（identifying relationship）。有自己的鍵的實體型態，稱為**強實體型態**（strong entity type）。

#### 部分鍵

弱實體雖然沒有鍵，但在**同一個擁有者**底下，通常有一個屬性可以區別彼此：同一位教師的眷屬姓名不會重複。這個屬性稱為**部分鍵**（partial key，又叫鑑別子 discriminator），畫成**虛線底線**。

弱實體的完整識別方式是「**擁有者的鍵 ＋ 部分鍵**」：(教師編號 iid, 眷屬姓名 dep_name)。

#### 畫法與限制

- 弱實體型態畫成**雙矩形**，識別關係畫成**雙菱形**。
- 弱實體在識別關係中**一定是完全參與**（雙線）：沒有擁有者的眷屬不存在。教師離職、資料刪除時，他的眷屬資料也一起刪除。
- 識別關係通常是 1:N：一位教師可以有多位眷屬，每位眷屬屬於一位教師。

#### 反例：完全參與不等於弱實體

學生在「屬於」中也是完全參與（每位學生都要屬於一個系），但學生**不是**弱實體，因為學生有自己的鍵 sid，不需要靠系來識別。判斷弱實體看的是「**能不能自己識別**」，不是「是不是完全參與」。

### 特殊化與一般化

#### 為什麼需要特殊化

學生和教師都是學校的「人員」，都有身分證字號、姓名、生日；但學生另外有年級，教師另外有職稱；而且只有研究生才有指導教授。如果把學生和教師畫成兩個無關的實體，共同的屬性要寫兩次；如果全部塞進一個「人員」實體，又無法表達「只有研究生才有指導教授」。

基本的 ER 模型加上類別階層之後，稱為**擴充 ER 模型**（enhanced ER，EER）。

#### 父類別與子類別

> **定義**：如果實體型態 B 的每個實體都是實體型態 A 的一個實體（「是一種」，is-a），就說 B 是 A 的**子類別**（subclass），A 是 B 的**父類別**（superclass）。子類別**繼承**（inheritance）父類別的所有屬性與關係，並可以有自己專屬的屬性與關係。

同一個階層可以從兩個方向得到：

- **特殊化**（specialization）：由上而下。從「人員」出發，依身分分出「學生」與「員工」。
- **一般化**（generalization）：由下而上。先有「汽車」與「機車」，發現它們有共同的屬性（車牌、廠牌），抽出共同的父類別「車輛」。

兩者畫出來的圖一樣，差別只在設計時思考的方向。

#### 兩個限制

特殊化要回答兩個問題：

1. **一個實體能不能同時屬於多個子類別？** 不能的是**不相交**（disjoint），圓圈裡寫 d；可以的是**重疊**（overlapping），圓圈裡寫 o。
2. **父類別的每個實體，是不是一定屬於某個子類別？** 一定的是**完全特殊化**（total specialization），父類別到圓圈畫雙線；不一定的是**部分特殊化**（partial specialization），畫單線。

兩個問題各有兩種答案，共四種組合：

| | 完全 | 部分 |
|---|---|---|
| **不相交** | 學生 → 大學部、研究生：每位學生恰好是其中一種 | 員工 → 秘書、技術員：員工最多是其中一種，也可以都不是 |
| **重疊** | 書 → 紙本、電子：每本書至少有一種版本，也可以兩種都有 | 人員 → 學生、員工：助教既是學生也是員工；訪客兩者都不是 |

#### 限制

完全／部分特殊化和上一節的完全／部分參與都用雙線表示，但問的是不同的事：參與限制問「每個實體是否都參與這個**關係**」，特殊化的完全性問「每個父類別實體是否都屬於某個**子類別**」。看雙線畫在哪裡（關係的線上，還是父類別到圓圈的線上）就能分辨。

### ER 圖轉關聯綱要

#### 先認識主鍵與外鍵

轉成表之前，先介紹兩個第 3 章會詳細說明的名詞：

- **主鍵**（primary key）：從表的鍵中選一個，用來唯一識別每一列。寫綱要時在主鍵下加底線，例如 Student(<u>sid</u>, name)。
- **外鍵**（foreign key）：表中的一個（或一組）欄位，它的值必須是另一個表（或同一個表）某一列的主鍵值。外鍵用來表示「這一列和那一列有關係」，本章寫成「dname → Dept」，意思是 dname 參照 Dept 的主鍵。

ER 圖裡的「關係」，轉成表之後大多變成外鍵。

#### 轉換的步驟

**目標**：把圖 2-2、圖 2-4 的學校 ER 圖轉成一組表，每個表標出主鍵與外鍵。實體的屬性如下：系 Dept(<u>dname</u>, phone)、教師 Instructor(<u>iid</u>, name)、學生 Student(<u>sid</u>, name（first、last）, phone（多值）, birthday, age（衍生）)、課程 Course(<u>cid</u>, title, credits)、弱實體眷屬 Dependent(dep_name（部分鍵）, relation)；主管關係有屬性 since（開始擔任主管的日期），修課有 grade。

**想法**：先把每個「東西」變成表，再依關係的基數比決定「關係」放在哪裡：能用外鍵表示的就加欄位，不能的才開新表。

**步驟 1：強實體。** 每個強實體型態一個表。簡單屬性直接放；複合屬性只放最底層的子屬性；**衍生屬性不放**（需要時再算）；多值屬性留到步驟 6。選一個鍵當主鍵。

- Dept(<u>dname</u>, phone)
- Instructor(<u>iid</u>, name)
- Student(<u>sid</u>, first_name, last_name, birthday)：name 拆成兩欄，age 不放，phone 留到步驟 6
- Course(<u>cid</u>, title, credits)

**步驟 2：弱實體。** 每個弱實體型態一個表，放自己的屬性，再加上擁有者的主鍵當外鍵。主鍵是「擁有者的主鍵 ＋ 部分鍵」。

- Dependent(<u>iid, dep_name</u>, relation)，iid → Instructor

**步驟 3：1:1 關係。** 在其中一邊的表加上另一邊的主鍵當外鍵，關係的屬性跟著放。**優先放在完全參與的那一邊**。

- 主管：系是完全參與，所以在 Dept 加 mgr_iid → Instructor 與 mgr_since。

為什麼放 Dept？假設有 50 位教師、5 個系。放在 Dept，5 個系每個都有主管，mgr_iid 沒有空值；如果反過來在 Instructor 加「主管哪個系」，50 位教師中只有 5 位是主管，其餘 45 列都是 NULL。

**步驟 4：1:N 關係。** 在 **N 那一邊**的表加上 1 那一邊的主鍵當外鍵，關係的屬性也放在 N 那一邊。

- 屬於：學生是 N 那一邊，所以在 Student 加 dname → Dept。

為什麼不放 Dept？一個系有很多學生，放在 Dept 就得在同一格裡塞進很多個學號，違反「一格只放一個值」（第 6 章的第一正規化）。放在 Student，每位學生只屬於一個系，一格一個值剛好。

**步驟 5：M:N 關係。** 兩邊都可能有很多個，外鍵放哪邊都不行，所以**開一個新表**：放兩邊的主鍵（各自是外鍵），兩者合起來當主鍵；關係的屬性放在這個表。

- 修課：Enroll(<u>sid, cid</u>, grade)，sid → Student，cid → Course
- 先修是課程對課程的 M:N，同樣開新表，兩個欄位都參照 Course，用角色區分名稱：Prereq(<u>cid, pre_cid</u>)，cid → Course，pre_cid → Course

**步驟 6：多值屬性。** 每個多值屬性開一個新表，放擁有者的主鍵（外鍵）和這個屬性，兩者合起來當主鍵。

- StudentPhone(<u>sid, phone</u>)，sid → Student

**步驟 7：三元以上的關係。** 開一個新表，放所有參與者的主鍵當外鍵。主鍵通常是全部的外鍵合起來（如果某一端的基數是 1，主鍵可以少放那一個）。學校的例子沒有三元關係；供應的例子會轉成 Supply(<u>sid, pid, jid</u>)。

**結論**：學校的 ER 圖轉成 8 個表（4 個強實體、1 個弱實體、2 個 M:N 關係、1 個多值屬性；1:1 與 1:N 關係沒有產生新表）：

```
Dept(dname, phone, mgr_iid, mgr_since)           mgr_iid → Instructor
Instructor(iid, name)
Student(sid, first_name, last_name, birthday, dname)   dname → Dept
Course(cid, title, credits)
Dependent(iid, dep_name, relation)                iid → Instructor
Enroll(sid, cid, grade)                           sid → Student, cid → Course
Prereq(cid, pre_cid)                              cid → Course, pre_cid → Course
StudentPhone(sid, phone)                          sid → Student
```

（程式碼區塊無法加底線，主鍵依序是：dname、iid、sid、cid、(iid, dep_name)、(sid, cid)、(cid, pre_cid)、(sid, phone)。）

考試常問「**最少需要幾個表**」，就是照這七個步驟數：每個強實體、弱實體、M:N 關係、多值屬性、三元以上的關係各一個表；1:1 與 1:N 不用新表。

#### 步驟 8：特殊化

EER 的類別階層有四種轉法，以「人員 → 學生、員工」為例：

| 做法 | 表 | 適用 |
|---|---|---|
| A. 父、子類別各一表 | Person(<u>pid</u>, name)、Student(<u>pid</u>, grade)、Employee(<u>pid</u>, title)；子類別的 pid 同時是參照 Person 的外鍵 | 任何情況都可以 |
| B. 只有子類別的表 | Student(<u>pid</u>, name, grade)、Employee(<u>pid</u>, name, title)，各自帶上父類別的屬性 | 只適合**完全且不相交** |
| C. 單一表＋類型欄 | Person(<u>pid</u>, name, type, grade, title) | 適合**不相交** |
| D. 單一表＋旗標 | Person(<u>pid</u>, name, is_student, is_employee, grade, title) | 適合**重疊** |

為什麼 B 只適合完全且不相交？如果是部分特殊化，不屬於任何子類別的人（訪客）沒有表可以放；如果是重疊，助教的 name 會在 Student 和 Employee 各存一次，又回到第 1 章的資料重複。C 和 D 只有一個表，不屬於某個子類別的列，那個子類別專屬的欄位就是 NULL（員工的 grade 是 NULL）。

#### 限制：有些限制轉不過去

外鍵只能表達一部分的 ER 限制。例如系在「主管」中的完全參與，可以用「mgr_iid 不可以是 NULL」（`NOT NULL`）表達；但如果系在「屬於」中也是完全參與（每個系至少要有一位學生），外鍵放在 Student，Dept 這邊沒有欄位可以檢查，光靠表的定義做不到，需要第 5 章的觸發程序或由應用程式檢查。

### 常見陷阱

- **基數比和 (min, max) 的標記位置相反**：基數比的 N 寫在「多」的那個實體旁邊，(min, max) 的 N 寫在「參與很多次」的那個實體旁邊。
- **關係的屬性不屬於任何一個實體**：成績屬於「修課」。轉成表時，1:N 的關係屬性放 N 那一邊，M:N 的放新表。
- **1:N 的外鍵放在 N 那一邊**，1:1 的外鍵優先放在完全參與的那一邊。
- **完全參與不等於弱實體**：弱實體是沒有自己的鍵；弱實體表的主鍵是「擁有者的主鍵 ＋ 部分鍵」，不是只有部分鍵。
- **衍生屬性不轉成欄位**，多值屬性要另開一個表；複合屬性只放最底層的子屬性。
- **三元關係不能任意拆成三個二元關係**，拆開後可能推出原本沒有的組合。
- **特殊化只用子類別的表（做法 B）**，只適合完全且不相交的特殊化。

### 專有名詞

| 名詞 | 英文 | 說明 |
|---|---|---|
| ER 模型 | entity-relationship model | 用實體、屬性、關係描述資料的概念資料模型 |
| 實體 | entity | 現實中可以區別的一個對象 |
| 實體型態／實體集合 | entity type／entity set | 一類實體的共同結構／某一時刻這類實體的集合 |
| 屬性 | attribute | 描述實體或關係的性質，畫成橢圓 |
| 簡單屬性／複合屬性 | simple／composite attribute | 不能再拆／由子屬性組成，例如姓名＝姓＋名 |
| 單值屬性／多值屬性 | single-valued／multivalued attribute | 每個實體一個值／可以有多個值，畫成雙橢圓 |
| 儲存屬性／衍生屬性 | stored／derived attribute | 實際存下來／可以算出來，畫成虛線橢圓 |
| 鍵屬性 | key attribute | 值不重複、可以識別每個實體，加底線 |
| 空值 | NULL | 值未知或不適用 |
| 關係／關係型態 | relationship／relationship type | 實體之間的關聯；同一類的關係歸為關係型態，畫成菱形 |
| 分支度 | degree | 參與關係的實體型態個數 |
| 二元／三元關係 | binary／ternary relationship | 兩個／三個實體型態參與的關係 |
| 遞迴關係 | recursive relationship | 同一個實體型態出現兩次，要標角色 |
| 角色 | role | 實體在關係中扮演的身分，例如先修課 |
| 基數比 | cardinality ratio | 一個實體最多對應另一端幾個實體：1:1、1:N、M:N |
| 完全參與 | total participation | 每個實體都必須參與，畫成雙線；又叫存在相依 |
| 部分參與 | partial participation | 實體可以不參與，畫成單線 |
| (min, max) 表示法 | (min, max) notation | 標在 E 那端，表示 E 的每個實體參與幾次 |
| 弱實體型態 | weak entity type | 沒有自己的鍵，要靠擁有者識別；畫成雙矩形 |
| 強實體型態 | strong entity type | 有自己的鍵的實體型態 |
| 識別擁有者 | identifying owner | 弱實體依附的實體型態 |
| 識別關係 | identifying relationship | 連接弱實體與擁有者的關係，畫成雙菱形 |
| 部分鍵 | partial key | 同一個擁有者底下能區別弱實體的屬性；又叫鑑別子 |
| 擴充 ER 模型 | enhanced ER，EER | 加上父類別、子類別階層的 ER 模型 |
| 父類別／子類別 | superclass／subclass | 子類別的每個實體都是父類別的實體（is-a） |
| 繼承 | inheritance | 子類別擁有父類別的所有屬性與關係 |
| 特殊化 | specialization | 由上而下，從父類別分出子類別 |
| 一般化 | generalization | 由下而上，抽出共同的父類別 |
| 不相交／重疊 | disjoint／overlapping | 一個實體最多屬於一個子類別（d）／可以屬於多個（o） |
| 完全特殊化／部分特殊化 | total／partial specialization | 父類別的每個實體是否一定屬於某個子類別 |
| 主鍵 | primary key | 選來唯一識別每一列的鍵，加底線 |
| 外鍵 | foreign key | 值必須是另一個表某列主鍵值的欄位 |
